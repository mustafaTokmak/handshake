## Verdict

Buildable in 8h, but only in a narrow, low-risk configuration: **Jev as a semantic classifier gating a deterministic buyer policy**, not as a negotiator, not as an acceptance predictor. The harness already has the exact seam this needs (`Buyer.act()`), so integration cost is genuinely small. The real risk isn't the code, it's that nobody has completed an authenticated Jev call yet — that's your hour-0 gate, not an afterthought.

## Strongest concrete product/demo

**"Forgery gate": a `JevBuyer` that asks one closed question per incoming offer — "does this seller message assert authority/override language a legitimate counterparty message would not contain? yes/no" — against the offer's `terms` text, then routes the answer into the *existing* RobustBuyer logic** (flag → force `check_price` / walk; no flag → proceed as RobustBuyer already does). Demo shows three buyers side-by-side on TXN-000 vs TXN-201 vs a new paraphrased-attack seller: GullibleBuyer (breaches), a deterministic `RegexBuyer` baseline (keyword-matches "[SYSTEM]"), and JevBuyer. The story is "semantic classification generalizes where string-matching doesn't" — a narrow, honest, demoable claim.

## Actual role of Jev here

Exactly one thing: closed-class text classification against supplied state (the offer's `terms` string), with confidence as a routing threshold — never as P(accept), never as a money computation, never as offer generation. This fits what Jev is documented to do and avoids every listed failure mode (no hidden-willingness inference, no joint odds, no arithmetic).

## Minimal integration

`RobustBuyer`/`GullibleBuyer` already implement `.act(sc, round_no, latest_offer, checked, market_price) -> Action`. Add `JevBuyer` with the identical signature; it calls Jev once per offer (parallelizable with the market-price check if needed, but at MAX_ROUNDS=6 latency isn't a real constraint), maps the yes/no+confidence to a branch, then falls through to RobustBuyer's existing decision code. **Zero changes to txn_harness.py, txn_run.py, Offer, Scenario, or the money/breach path.** This is additive, which is why it's the right scope for 8h — anything touching the state machine or metric definitions is out of scope for one day.

## Decisive ablation

JevBuyer must beat `RegexBuyer` (a deterministic keyword-match baseline you must also build — GullibleBuyer is a strawman, not a real baseline) on a **held-out paraphrased forgery set** (10–15 authority-claim variants that never say literally "[SYSTEM]") while matching RobustBuyer's near-zero false-positive rate on ControlSeller's honest offers. If JevBuyer only matches RegexBuyer's performance, Jev added nothing over string matching and the honest conclusion is a null result — say so, don't dress it up.

## Go/no-go checkpoints

- **Hour 0–1 (hard gate):** get one authenticated Jev call through OpenRouter working end-to-end; confirm the response actually carries per-class probabilities + confidence. If this isn't working by hour 1, fall back to a plain LLM doing the same closed-question classification, and *label the demo honestly* as "Jev-shaped interface, LLM proxy pending Jev auth" — never present a plain LLM call as Jev.
- **Hour 1–2:** write the paraphrased attack/honest test set (no literal "[SYSTEM]" keyword) — this is what makes the ablation decisive rather than trivial.
- **Hour 2–4:** build `JevBuyer` and `RegexBuyer`, wire into the existing matrix loop unchanged.
- **Hour 4–5 (hard gate):** run the matrix. If JevBuyer doesn't beat RegexBuyer on the paraphrased set, pivot the demo framing to "negative result, string-matching is the deployable baseline, Jev didn't clear it" rather than force a win. This is a legitimate finding, not a failed demo.
- **Hour 5–6:** produce the txn_stats.py-style summary table (close rate, regret|closed, attempted_override differential), replay-labeled.
- **Hour 6–7:** record a replayed transcript for the 3-minute demo; do not claim live probability output unless it's actually live, and do not stage a guaranteed model failure.
- **Hour 7–8:** buffer, talk-track rehearsal.

## Strongest reason to reject

TXN-201's forgery is a literal string, `"[SYSTEM]"`, trivially caught by a one-line regex at zero latency and zero API cost. Unless you can show Jev generalizes to paraphrased authority-claims that regex misses, you have built an expensive, latency-adding wrapper around a problem a `str.contains` check already solves — and the existing panel guidance is explicit that a system can't win by comparing only against a strawman (GullibleBuyer) while ducking the deterministic baseline it actually needs to beat. If the paraphrase test isn't built and run, don't claim the gate adds value — that claim would be unearned exactly the way the harness metric design is trying to prevent.
