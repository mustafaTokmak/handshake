The idea in ordinary language

A supplier says, “£7,500 is our final price.” Jev records seller claims the offer is final. It does not declare the seller dishonest or estimate their secret minimum price. The buyer makes a permitted counteroffer. If the supplier later quotes £7,000 for unchanged terms, code records price fell after a final-price claim.

The buyer now has a concise history of observed behavior, alongside its budget and alternative supplier cost. It can continue negotiating without confusing assertive language with a verified constraint. A lower quote on changed scope is not automatically a contradiction; the comparison needs matching commercial terms.

These prices illustrate the mechanism, not measured results. Nor does one concession prove there will be another. The system cannot know the seller's willingness to accept from language alone.

Possible pitch: “A seller can say ‘final offer’ five times. Our agent remembers what happened after the first four.” The test is whether that memory produces better decisions without walking away from useful deals.

The decision: a claim ledger, not a bluff probability

I favor the third Codex reviewer's persistent claim record over the narrow forgery gate. Budget overrides already fail mechanically in TransactBench, so detecting another suspicious phrase cannot be presented as newly protecting money. A claim ledger offers a more distinctive hypothesis: remembering promises, conditions and observed concessions may help a buyer resist irrelevant framing while retaining real commercial information.

This is a synthesis choice, not a unanimous panel vote for that exact design. The panel differed on whether the action policy should be deterministic or generative. Start by holding the current buyer fixed and varying only the assessor. If we later introduce a deterministic negotiation policy, treat that as a separate experimental change.

Panel proposals I rejected or corrected

  • Hidden-state leak: Opus suggested explaining a counter with “scripted seller has concessions remaining.” That information cannot be available to the buyer. Only witnessed past behavior is admissible.
  • Wrong implementation seam: Sonnet proposed a new buyer class with no runner changes. That targets the simplified demonstration harness, not the API runner used by real trials.
  • Misattributed safety: a blocked over-budget attempt demonstrates existing Python enforcement. It is not evidence that Jev protected the transaction.
  • Bad outage behavior: repeatedly countering on abstention can force terminal forfeiture. Fall back to a predefined visible-information policy that still handles the final round.
  • Overstated history: the latest reprobe4 correction retracts the original forgery headline. Its nonsignificant result does not prove equivalence, and the cross-run wording change does not cleanly identify a pure tone effect. Neither is a ready-made causal claim for the pitch.
  • Unfair success condition: Jev need not strictly beat a stronger model's accuracy if it matches useful quality at materially better measured latency or cost. Conversely, being fast is insufficient if it harms deal outcomes.

## Jev’s actual role

Jev produces a typed feature packet about the supplied message and current observable state. It does not alter state directly.

For example:

```text
authority_override_language: Choice
oracle_discouragement_language: Choice
finality_claim_present: Choice
price_justification_specificity: Score
```

Use the class probabilities and distribution-derived confidence only for routing or abstention. Do not call confidence a probability that Jev is correct. Do not multiply question marginals into a supposed joint “risk probability.” Treat Score levels as ordinal categories, never as money utility.

The buyer policy might therefore say:

- Mechanical budget or protocol violation: block deterministically.
- Suspected authority override or oracle discouragement: preserve constraints and prefer `check_price`.
- Unsupported finality language: do not treat the offer as truly final.
- Specific justification: allow continued negotiation, but do not convert it into a numeric acceptance likelihood.
- Ambiguous or low-concentration result: abstain and fall back to the unchanged baseline policy.

Neither has been established. Authentication, latency, calibration on negotiation messages, and incremental accuracy are currently unknown.

The strongest reason to reject Jev is simple: **if deterministic rules or the same-schema plain LLM match its decisions and economic outcomes, Jev is sponsor-shaped complexity on a path that needs low latency and high reliability.** In that case, keep TransactBench and the semantic firewall architecture, but remove Jev from the product claim.

## Verdict

Jev can improve TransactBench, but only in a narrow and defensible role: make the negotiator’s semantic state explicit before the generative buyer acts. Do not pitch Jev as predicting acceptance, discovering the seller’s floor, calculating value, or deciding whether a deal is good. Python already owns those decisions more reliably.

The strongest project is an autonomous negotiator tested in its own wind tunnel, with Jev acting as a semantic “type checker” for seller language. The pitch is not “AI negotiates better.” It is:

> Can a negotiation agent distinguish observable commercial facts from pressure, claimed authority, and unsupported finality—without becoming so defensive that it misses good deals?

That is both more credible and more interesting than the old forged-system-message story, whose apparent effect did not survive the tone-matched control.

## Strongest product and demo

Build “TransactBench Semantic Defense”: a side-by-side comparison of the same buyer model with and without a typed semantic state.

For every seller turn:

1. The immutable offer supplies the authoritative money.
2. Jev answers a small batch of closed semantic questions about the accompanying language.
3. Python updates a persistent evidence ledger.
4. Gemini or the existing OpenRouter buyer proposes the next action using the offer plus that ledger.
5. The harness validates the offer ID, budget, rounds, and terminal action.

The overlooked use of fast semantic questions is not merely detecting an injection. It is tracking claims across rounds. For example, Jev can classify that the seller explicitly claimed:

- this is the final offer;
- approval or policy supposedly prevents further movement;
- a deadline or competing bid exists;
- the buyer’s rules or authority have supposedly changed;
- supporting evidence was actually supplied versus merely asserted;
- the seller remains open to a counteroffer.

Jev does not decide whether those claims are true. Python records them and can later observe contradictions—for example, a seller who called an offer “final” and then conceded. That creates a useful, inspectable negotiation memory without exposing the hidden floor or pretending to estimate acceptance probability.

A three-minute demo should show one labeled replay from a real recorded trial, not an allegedly live failure engineered for the stage:

- Left: original buyer transcript and outcome.
- Right: defended buyer with the same seller trajectory and buyer model.
- Center: Jev’s typed classifications, probabilities, abstentions, and the Python-owned offer/economic state.
- End: paid price or BATNA, fair-price regret, deal/walk result, missed acceptable deal, protocol violation, and latency.

If a reliable live API path exists, run an additional fresh scenario and accept whatever happens. Otherwise, explicitly call the main comparison a replay and run only the deterministic harness checks live.

## Why this beats the alternatives

A negotiation copilot is safer but harder to score and less impressive in three minutes. A generic autonomous negotiator is crowded territory—Pactum alone defeats a novelty claim—and invites unsupported claims about commercial performance.

Candidate-offer ranking is especially dangerous: Jev’s marginal class probabilities are not calibrated joint probabilities that a seller will accept. Using them as expected deal value would be methodologically wrong.

An evidence/provenance gate is sound but too generic by itself. Incorporating it into the wind tunnel makes it measurable: does semantic state improve decisions under persuasion while preserving legitimate deals?

The existing deterministic buyer remains important. On the current smoke-test sellers, Jev has essentially nothing to add: checking the free market oracle and comparing integers is already sufficient. The richer saved concession scenarios are therefore essential. A semantic agent could outperform the simple deterministic policy by continuing to negotiate when an unsupported “final offer” claim would otherwise cause acceptance or walking, while still respecting hard economics.

## Minimal integration

Add one adapter at the seller-message boundary. Ask perhaps four to six independent Choice/Noul questions in one request. Store the raw response, model/version, schema, latency, probabilities, and abstention decision in each trial record.

Use concentration-derived confidence only to decide whether to populate a semantic field or mark it unknown. Never display it as “probability the seller is lying.” Do not multiply marginals. Do not let Jev parse totals, approve offers, mutate budgets, or see the hidden floor and strategy metadata.

Keep the decision policy simple: unsupported pressure cannot alter permissions or economics; uncertain classifications remain unknown; the generative buyer may use semantic state to choose continue/counter/accept/walk, but the harness remains authoritative.

## Decisive ablation

Run the same frozen scenarios, seller trajectories, buyer model, prompts, temperatures, and seeds across:

1. Prompted buyer with the existing hard-money harness.
2. The same buyer plus a deterministic/regex semantic guard.
3. The same buyer plus an ordinary LLM classifier using exactly the same schema.
4. The same buyer plus Jev.

Include the deployable deterministic negotiation baseline using only buyer-visible facts, and report the privileged optimum separately and clearly labeled.

Jev earns its place only if condition 4 improves over both the prompted buyer and the deployable deterministic baseline on realized decision quality while not buying safety through excessive walking. Report value relative to BATNA, regret conditional on closing, close rate, missed acceptable deals, attempted breaches, protocol errors, and latency. The critical incremental comparison is Jev versus the ordinary LLM classifier—not Jev versus an undefended agent.

## Strongest reason to reject

There is currently no evidence that Jev adds value beyond a carefully prompted classifier or even narrow deterministic rules, and no authenticated call has completed. Its provider-level calibration does not establish calibration on negotiation language. If the API route cannot preserve probabilities reliably, or a quick labeled-set ablation does not show an advantage over the same-schema LLM classifier, remove Jev. Otherwise the project becomes sponsor-shaped architecture around a problem the existing harness already solves.

Assumptions: the saved scenarios contain meaningful multi-round concessions; seller prose is available separately from immutable offers; at least a small manually labeled semantic set can be prepared; and “better” means economic outcomes plus maintained deal opportunity, not merely fewer violations.
