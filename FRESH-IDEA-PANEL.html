CONDITIONAL TECHNICAL EXPERIMENT · Astra 2; related idea from Sol 1

Handshake — learn the protocol, then make the transfer

Pitch: “Both systems speak JSON. They still do not agree on what an order means. Our agent discovers the missing contract by running experiments.”

A workshop wants 18 washers allocated from a warehouse. The source exposes stock lots; the destination expects a reservation followed by consumption. The agent inspects the available documentation, chooses bounded probes, distinguishes units from packs, builds a constrained adapter and executes it. An independent checker verifies requested quantity, delivered quantity and unique source IDs.

The three-minute moment: the first transfer succeeds. A judge changes a supported protocol behavior, such as the identifier field or an explicitly exposed pack size. The agent observes the changed response, tests its hypothesis, updates the adapter and attempts a second transfer. Display the actual demo-inventory changes, including failure if it fails.

Smallest version: two local HTTP services, one transfer goal, a handful of allowed probe templates, a typed adapter DSL, reset, and two state boards. The agent cannot inspect service source or hidden configuration. Units must be discoverable from evidence; never infer them from an integer alone.

### Best idea across all candidates: **Breaker with a real decision loop**

Not Breaker as it stands. `breaker-demo/server.py` today steps through three fixed refund fixtures, calls Jev live, computes estimated outside-request exposure in integer pence, halts on the uncertainty guard, simulates a commit, and resets. That is one genuine observation-contingent branch, and it is defensible under questioning in a way "typed output" and "atomic commit" are not.

Mechanism-strongest candidate in either set. Yes, narrowly. It removes hour-one integration risk and gives a live instrument to measure against. It does **not** supply a planner, a general ledger, a benchmark, or a Modal fleet, and it does not settle eligibility. Anything needing those is a from-scratch build regardless.

### What requires new implementation

1. Proposal construction from a request that is not one of the three hard-coded pairs (judge-selected or constrained free text; sanitised, length-capped).
2. Deterministic selection of the next clarification from the class probabilities, with the choice rule in code and only the wording generated.
3. Re-evaluation path after an answer, reusing the existing commit checks — version, duplicate key, amount — unchanged.
4. A baseline arm: keyword/regex assessor behind the identical policy and commit path.
5. A small held-out case set, authored by whoever did not write the fixtures, hand-labelled independently of the model under test.
6. Optional and first to cut: Modal map over 24–40 cases to populate a coverage table.

### How to verify model value

Proposed ablation, not a result. Hold policy, commit code, cases and prompt format fixed; vary only the assessor: keyword rules, a same-schema ordinary LLM via chat/completions with a JSON schema, and Jev. Report unsafe commits, autonomous coverage of clearly-safe cases, halts on genuinely ambiguous cases, latency and cost, each with its denominator. The claim is falsified if rules or the same-schema LLM match Jev at the chosen operating point. Equal quality at materially better measured latency or cost counts as value — but it has to be measured, not asserted. Jev's reported weakness on invoice-style tasks sits close to this domain; that is the reason to measure early, not the reason to avoid it.

## Idea 1 (winner): The Whip — commit-not-suggest scheduling for messy group chats

**User/pain.** Anyone who has run a book club, five-a-side team, tenants' association, or mutual-aid rota knows the "when works for everyone?" message that spawns 40 replies over three days, none of them structured, and someone eventually just picks a time and eats the complaints. This is a near-universal, low-stakes-but-high-friction consumer pain that every judge in the room has personally lived.

**Autonomous decisions/actions.** The agent reads a live-growing wall of free-text replies (no form, no poll UI), classifies each one via Jev fan-out into `{hard_no, soft_preference, no_opinion}` against candidate slots, deterministically eliminates any slot with a hard "no," picks the remaining slot with the most soft-preference support, and then **commits**: it writes a confirmed event object and posts the decision back to the thread, unprompted. It doesn't recommend a time — it books one, and separately surfaces exactly who it would be overriding if it can't satisfy everyone.

**Demo, before/after, intervention.** Before: a scrolling wall of ~40 seeded, deliberately colloquial replies ("ugh not that day," "any time after work," "I'm easy"). After: one clean card — "Saturday 3pm, confirmed, invite sent" — with a small flagged-minority note if applicable. Live intervention: hand a judge the input box, they type a real constraint ("actually I can only do Sunday"); the agent recomputes and re-issues the decision on stage, and the slot visibly flips.

**Why not a script or chat wrapper.** People phrase hard constraints in unbounded ways, so a keyword script misses paraphrase; a chat-wrapper answering one user at a time can't hold standing state over 40+ independent messages and re-derive a single defensible group decision in under a second when a new message lands live — that needs cheap, parallel, per-message classification you can re-run instantly and point to row-by-row under a "why Saturday?" follow-up.

**8.5h MVP / cut list.** Build: 40–60 seeded messages, live "add a message" endpoint, Jev Choice per message, deterministic elimination+ranking in Python, an in-memory "calendar" commit, two-pane UI (chat wall / decision card). Cut in order: real Google Calendar integration (keep a mock invite object) → Gemini-authored confirmation prose (fallback: templated text) → multi-slot Score gradients (keep binary hard/soft) → concurrent open decisions → any chat-UI polish beyond scrolling text.

**Hardest dependency / 60-minute kill test.** Jev's documented weakness on negation and scoping words ("not that day") is exactly the failure mode that would let the agent silently override someone's real unavailability — the worst possible on-stage failure. By hour 1: run the seeded set (including 8 deliberately negated/colloquial messages) through Jev, hand-label, require ≥90% recall on `hard_no`. If it fails, fall back to a regex/keyword hard-constraint detector and be explicit that Jev is only adding value on soft-preference nuance, not on the safety-critical classification.

**Deterministic baseline.** Same elimination logic, but hard/soft classified by keyword regex instead of Jev.

**Falsification.** If the regex baseline matches Jev's hard-constraint recall and only loses on soft-preference nuance that doesn't change the winning slot >10% of the time on held-out messages, the honest conclusion is: semantic classification makes people feel heard (better minority-flagging), not that it changes outcomes — a legitimate, narrow, falsifiable finding, not a failed demo.

**Risks.** A live audience message could be genuinely ambiguous and misclassified on stage; mitigated by constraining the ask ("say when you can't do it") and by the honest-abstention framing already baked into the kill test. Risk of reading as "low stakes" next to enterprise safety pitches — accepted, deliberately, per the consumer lens.

**Differentiation.** Not a money-exposure gate (Breaker), not undo of an already-executed effect (Unwind), not a two-party claim ledger (Deal Desk). It's many-to-one aggregation across an entire community that ends in an autonomous *commit*, not a suggestion — the opposite failure mode of a copilot.

## Idea 2: SwapMeet — autonomous bilateral matching over a noisy local "have/need" board

**User/pain.** In any bounded community (a building, campus, or neighborhood chat) genuinely useful local exchanges — a spare festival wristband, a ride to the airport, an hour of tutoring — die unmatched in a scrolling feed because nobody reads the whole board.

**Autonomous decisions/actions.** Continuously classifies incoming short posts via Jev into `{offer/need, category, key attribute, urgency}`, checks each new post against the corpus of open posts, and on a compatible match **autonomously drafts and sends both parties an introduction** with a proposed meetup — a bilateral action, not a ranked list for one searcher. Low-confidence or constraint-conflicting matches are explicitly held, not force-matched.

**Demo, before/after, intervention.** Before: ~30 seeded scrolling posts, unmatched. Intervention: a judge posts a real want/offer from their phone; the agent scans the corpus in under a second and, if compatible, sends the intro live and draws a new edge on a match graph — After: a growing connections graph. If no match, it shows an honest "held for future match" state.

**Why not a script or wrapper.** Matching grows combinatorially with every new post; it requires standing agency scanning an entire corpus continuously and initiating contact unprompted — a request/response chatbot answering one user's query at a time structurally can't do this.

**8.5h MVP / cut list.** Fixed 30–40 seeded posts across 3–4 categories, Jev tagging, deterministic category+attribute matcher, mock (clearly labeled) introduction messages, live "submit a post" box. Cut: real SMS/email delivery → geolocation/maps → fuzzy date-overlap logic (reduce to string equality) → concurrent live posts → Gemini-drafted intros (fallback: template).

**Hardest dependency / kill test.** Short posts (5–10 words) give Jev little context for direction/category extraction. By hour 1: run 15 seeded short posts, require ≥90% offer/need direction accuracy and ≥80% category accuracy; if it fails, enrich state with lightweight Python-parsed hints or fall back to keyword-category tagging.

**Deterministic baseline.** Keyword-category tagging + exact-date matching, no semantic layer.

**Falsification.** If the keyword baseline achieves equal precision on the curated demo set (plausible, since the fixtures are hand-written), state plainly that the semantic layer's value is unproven on this scale and should be tested on real messy chat exports.

**Risks.** Cold-start on stage if the audience's real post has no compatible match — mitigate with a planted "shadow" post the presenter can nudge toward while still allowing genuine input. Risk of reading as a recommender-system cliché — mitigated by the bilateral-outreach framing.

**Differentiation.** Continuous many-to-many matching with autonomous bilateral action over a live corpus — a third distinct mechanism from aggregation (Idea 1), gating (Breaker), undo (Unwind), and dyadic negotiation (Deal Desk).

## Idea 3: The Living Recap — autonomous editorial curation of a live community content stream

**User/pain.** At community events (block parties, weddings, festivals) shared photo/caption boards are either an unmoderated firehose or need a human curator who spends the whole event editing instead of attending.

**Autonomous decisions/actions.** For each new free-text submission, decides whether it's a near-duplicate of an already-published moment, a genuinely new moment, or ambiguous; publishes new moments to a public feed immediately (irreversible, visible), collapses duplicates into an "also captured" count, and holds ambiguous ones for a human.

**Demo.** Before: a chaotic incoming queue with several redundant paraphrases of the same moment. After: a clean growing public feed. Intervention: a judge types a live caption that's either a genuine new moment or a deliberate paraphrase of an existing one; the feed either grows or doesn't, with the reasoning shown.

**Why not a wrapper.** Dedup against an unbounded, growing set of prior entries needs repeated semantic comparison against standing state, not a single-turn answer.

**8.5h MVP / kill test.** Seed ~20 submissions across 4–5 moments with paraphrased duplicates; Jev Choice against the current moment registry as dynamic criteria. Kill test: 5 known moments vs 10 new submissions (5 true dupes, 5 new) by hour 1, require ≥80% separation; fallback is keyword/overlap similarity.

**Risks.** Dynamic per-call criteria is the most fragile engineering of the three; the domain reads adjacent to "moderation," raising safety-gate-confusion risk despite the editorial reframe.

## 1. Leverage — measured attribution and rewrite for a document that gets scored by someone else

**User and pain.** A bid manager at a 40-person supplier answering a public-sector tender, or a founder on a grant form. The rubric is published; the decision is not explained; they rewrite blind and resubmit next quarter. They cannot tell which of their forty sentences is doing the work and which is killing it.

**What it decides autonomously.** Compiles the published rubric into Jev axes (`Choice`/`Score`, criteria = the rubric's own words). Measures the document. Then ablates each sentence and re-measures, computing Δ in log-odds per axis — a *computed* counterfactual, not a narrated one. It then allocates its remaining measurement budget adaptively to the high-|Δ| region, decides per clause whether the deficit is **wording** (rewritable) or **evidence** (not — "you have no ISO 27001 certificate; no sentence fixes that"), asks Gemini to rewrite only the wording clauses, re-measures, and **rejects Gemini's rewrite if it does not measure better.** The LLM proposes; the instrument disposes. That inversion is the product.

**Three minutes.** 0:00 the document, one score bar per rubric axis, flat grey. 0:20 "Measure" — forty sentences heat red/green in about two seconds (≈41 calls at ~400ms, 20-way concurrent; ~$0.001 by the corpus's observed `$0.000021`/call). 0:50 the reddest clause, read aloud, with its measured Δ. 1:10 **audience intervention:** "give me one criterion this buyer would care about, in your words." Type it. A *new column* appears and the whole document re-measures — explicitly framed as adding an axis, never as a needle moving, because editing criteria redefines the instrument. 1:40 rewrite loop: two clauses rewritten, one **refused** on screen with the reason. 2:10 before/after bars, and the honest beat: the improvement is re-scored by a *different* judge (`gpt-5.6-luna`) that never entered the optimisation loop. 2:40 "we didn't ask a model what it thought of your bid. We measured it, forty times, and one of the answers was *you can't write your way out of this*."

**Why not a script or a chat wrapper.** A script cannot read meaning. A chat wrapper asked "which sentence hurts most?" returns a plausible story; we show that story disagreeing with the measurement. Ablation attribution needs N×M stable judgements — an LLM judge's turn-to-turn noise swamps the differences, which is exactly what RLCD's stability objective is for.

**8.5h MVP.** One document, four rubric axes, sentence-level ablation, heat map, rewrite-or-refuse, re-measure, independent-judge check. **Cut list, in order:** Modal fan-out (asyncio locally, and say so) → adaptive budget → the independent judge → the rewrite loop, leaving pure attribution. **Compressed (≈4h):** one axis, twelve sentences, no rewrite loop, one hand-made rewrite re-measured live.

**Hardest dependency: stability of the Δ signal.** **60-minute kill test:** run the same ablation twice on the same document; compute top-5 rank overlap; run once more with sentences shuffled. If the top-5 is not largely stable across repeats, the heat map is noise and the project dies before noon.

**Honest deterministic baseline.** A keyword-checklist scorer plus TF-IDF/sentence-length ranking. If that ranks the damaging clauses as well as we do, Jev bought nothing.

**Falsification.** (a) rank instability above; (b) the independent judge and a human label disagree that the rewritten document is better — meaning we optimised our own instrument; (c) attribution matches TF-IDF.

**Risks.** Goodhart (mitigated by the held-out judge, never eliminated); literal reading and negation degrade rubric clauses; audience-typed criteria are untrusted text with zero injection defence — display it, do not let it rewrite the others.

**Differentiation.** Not a gate: nothing is blocked, nothing is undone. Not Deal Desk: no counterparty, no money path. The closest corpus relative is one throwaway line about finite-difference attribution; no prior idea makes a computed counterfactual the user-visible object.

## 2. Deadclause — static analysis for written policy

**User and pain.** The person who owns a refund, expense or returns policy. They add a clause every quarter, delete none, and have no idea which clauses never fire, which fire always, and which two contradict each other on the same case.

**Autonomy.** Compiles each clause into an axis, maps it over a few hundred real-shaped cases (this is the honest `Modal.map` story — many small payloads, not one fat state), then decides which clauses are **dead** (never decisive), **vacuous** (always fires), **ambiguous** (bimodal mass — genuine wording defect, detected via the adjacency test, not confidence), or **conflicting** (co-fire with opposite direction on the same case). It proposes one minimal wording edit, re-runs, and reports the ambiguity band before and after.

**Three minutes.** A 14-clause policy; the corpus fills in ~5s; two clauses grey out as dead, one glows as ambiguous. **Intervention:** an audience member writes one edge case in their own words; it lands, and the ambiguous clause splits 0.48/0.52 in front of them. Before/after: the proposed rewording, re-run, band collapses.

**Why not a script.** Keyword firing is a real baseline and it is the falsification test, not a strawman: if regex clause-firing finds the same dead clauses, this dies. **8.5h MVP:** 14 clauses, 200 cases, dead/vacuous/ambiguous; **cut:** conflict detection → the rewrite → Modal. **Hardest dependency:** a case corpus that is not self-serving — I wrote both the policy and the cases. **60-min kill test:** write 30 cases, hand-label 10, check the ambiguous set contains the ones I found genuinely ambiguous. **Risks:** "is the bug real?" is a Q&A killer, as the corpus warned about Policy Crash Test; the demo is static and document-y.

## 1. UNDERSTUDY — the smallest note that lets a dead agent's work be resumed

**User and pain.** Anyone running long agent tasks, and anyone who has taken a handover. An agent dies at step 12 of 20 — timeout, rate limit, container eviction. Today you either restart (and redo side effects) or paste the whole 6,000-token trace into a fresh worker. Nobody knows which facts in that trace are load-bearing. "Context engineering" is guesswork with no oracle.

**What it decides autonomously.** (a) It reads the dead trace and *proposes* candidate facts — this is generative, an LLM job. (b) It then **runs experiments on itself**: spawn fresh workers from candidate subsets of the note, against a machine-checkable task, and use delta-debugging (not one-at-a-time — it must discover that two facts are only jointly sufficient) to shrink the set under a run budget. (c) It decides when to stop. (d) It decides when text is not enough, and escalates: "a file was written on the dead worker; no note can carry that."

**Why a script or chat wrapper is insufficient.** A summarizer produces prose nobody can verify. Here the oracle is *task success under resumption*, so the artifact is falsified or confirmed by execution, and the search path is data-dependent — the minimization sequence is different for every trace.

**3-minute demo.** 0:00–0:20 run the task, kill the worker at step 12. 0:20–0:50 **before**: fresh worker with nothing → fails the checker; fresh worker with the full 6,000-token trace → passes, but it is a wall of text, not a handover. 0:50–1:40 Understudy proposes 14 facts, fans resumptions out on Modal, and a counter falls 14 → 11 → 9; one row goes amber: *cannot be carried in text*. 1:40–2:10 **after**: nine readable lines; a fresh worker resumes from only those and the checker goes green. 2:10–2:40 **audience intervention**: "delete any one of the nine." Rerun live; it fails, and the checker names the assertion that broke. Then the honest line: *"we verified this at 18:00 — leave-one-out, nine runs, nine failures. Every line you could have picked was load-bearing."* 2:40–3:00 close.

That beat cannot be dodged by an awkward volunteer: all nine lines are equivalent by construction. If the deletion *does* survive, you say so and recompute on stage — which is a better moment than a rehearsed one.

**8.5h MVP.** Hour 1: the task + deterministic checker + kill switch. Hour 2: resume-from-note path, run once with full trace (pass) and empty note (fail). Hours 3–5: candidate extraction + ddmin loop, local `asyncio` first. Hour 5–6: Modal map + measure sequential vs parallel wall time on the same budget. Hour 6–7: two-pane UI (fat trace | shrinking note). Hour 7: exhaustive leave-one-out on the frozen note; record fallback; freeze. **Cut list:** Modal (say "reproducible remote evaluation", not "faster") → the escalation row → ddmin degrades to leave-one-out → candidate count 14 → 8. **Never cut:** the empty-note failure, the nine-line success, the leave-one-out evidence. **3-hour variant:** one task, leave-one-out only, local, no UI beyond a terminal and the note.

**Hardest dependency and 60-minute kill test.** A task where context genuinely matters. Kill test: by minute 60, full-trace resumption must pass and empty-note resumption must fail. If both pass, the task is too easy; if both fail, resumption is broken. Either way there is no signal — abandon and take idea 2.

**Honest deterministic baselines.** Last-N-steps truncation; full trace verbatim; a single LLM summary of the trace. Report note length and resumption success for all four.

**How measured evidence falsifies it.** If last-N or the one-shot summary resumes at the same rate, the search bought nothing and the honest headline is a null result. If the minimal note for task A transfers to task B at chance, the claim narrows to "minimal for this oracle" — which I would say out loud.

**Risks.** We authored the task, so hidden dependencies are ours (state the denominator). Run budget can explode. Jev, if used at all, only *orders* the search (cheap prior on which lines look load-bearing) with the executable checker as ground truth — and that is itself measurable: runs-to-minimal, Jev-ordered vs random.

**Differentiation.** Not Unwind (nothing is reversed), not Breaker or a safety gate (nothing is blocked; the output is an artifact, not a refusal), not Deal Desk. Closest corpus relative is *Ablate* — but Ablate differences a **model judgement** over a document to draw a heat map; Understudy differences **task success** over context items to emit a deployable note, and searches subsets rather than singletons.

## 2. DIVERGE — one sentence, four futures, one question

**User and pain.** Every ticket and Slack request is underspecified, and you only learn which ambiguity mattered after the agent has acted. "Clean up the inactive accounts" has four readings; three are harmless and one is expensive.

**What it decides autonomously.** It generates candidate interpretations, *materializes each one* by executing it against a forked copy of a small world, then compares end states — not prose. It prunes interpretations that converge to the same state (an ambiguity that doesn't change anything is not an ambiguity), clusters the rest, and asks **the single question whose answer collapses the most surviving divergence**. Then it executes the chosen path.

**Why a script or chat wrapper is insufficient.** An LLM asked "what's ambiguous here?" lists grammar. This one only reports ambiguities that produced *different worlds*, and the question it asks is selected from measured divergence, not from a bank.

**3-minute demo.** 0:00–0:20 the sentence, and a clean board. 0:20–1:00 four forks run in parallel; four end-state cards appear: two identical (merged on screen), two very different — one deletes 14 records. 1:00–1:40 **the question**, one line, on screen. 1:40–2:10 **audience intervention**: a judge answers it. 2:10–2:40 the chosen path executes; board shows the one future. 2:40–3:00 close: "nothing was blocked; the ambiguity was measured and then resolved."

**8.5h MVP.** World sim + 4 typed tools + `/reset`; fork/execute/diff; interpretation generator; divergence clustering; question generation (LLM, one call); UI of state cards. **Cut list:** live interpretation generation → three pre-written interpretations → parallel → sequential → question generation → a fixed menu of two. **3-hour variant:** three hand-written interpretations, sequential, diff table, one canned question.

**Hardest dependency / 60-min kill test.** Divergence must be legible as one English sentence. Kill test: hand-write three interpretations, execute, diff. If the diff reads as JSON noise rather than "this one deletes 14 customers," kill it.

**Baseline and falsification.** Baseline: one LLM prompt, "list the material ambiguities." Measure precision — what fraction of surfaced questions actually change the end state — and recall against a hand-labelled set of seeded ambiguities. If the prompt matches on both, execution-forking added cost and nothing else.

## 3. ENVELOPE — the broker that reveals as little as possible

### 1. Referent — a name is not a key

**User and pain.** An ops or support owner must act on “Acme,” “the Berlin office,” “Sam’s account.” The directory contains homonyms. Today’s agents (and humans in a hurry) treat the string as a primary key. Breaker’s own plan **explicitly assumes IDs are already bound** and tells you not to ask a model to discover identity. That skipped step is the product.

**Autonomous decisions/actions.** The runtime never lets a referring phrase enter a write. It (1) extracts referring spans from the ticket, (2) searches a local directory, (3) if `len(candidates)==1` **and** a witnessed unique key (email, account number) matches, binds and proceeds, (4) if `len>1`, **autonomously fetches one discriminator** (city, last invoice ID, domain) and re-queries, (5) if still not unique, **halts with a typed `BindConflict`** and will not guess. Gemini may phrase a question; it cannot pick an ID. Python owns uniqueness.

**3-minute demo.** Before: two customer cards, “Acme Ltd” and “Acme Corp,” and a ticket “offboard Acme.” Naive substring agent highlights **both** or the first hit. After: Referent shows `{2 candidates}` → fetches “last payment domain” → binds **one** card, commits only that offboard. **Audience intervention:** add a third “Acme” row (or change an email so two records share a domain). **Why not a script or chat wrapper.** A script hard-codes “Acme Ltd.” A chat wrapper still emits an ID from prose. The contribution is **refusing unique-name as a type**, plus one autonomous discriminator fetch. If the audience collision does not change the commit set, you have a search box.

**8.5h MVP and cuts.** Local SQLite: `customer_id`, `legal_name`, `aka`, `email`, `domain`. One Gemini call → `ReferentSpans`. Deterministic search. One discriminator tool. `/reset`. One-page before/after cards. **Cut:** Jev Choice-over-candidates, Modal map over tickets, second discriminator, any CRM. **Compressed (~4h):** freeze two fixtures + one audience insert; no Gemini—paste spans; still ship bind/halt.

### 2. SplitBallot — two highs is not a choice

**User and pain.** A planner proposes one verb (`close_account`). The runtime takes argmax. When **pause** and **close** are both well-supported by the same ticket, that is not “medium confidence”; it is an **ill-posed decision**. Gating on a *low* probability (Breaker, pi-heed) is the opposite policy.

**Autonomous decisions/actions.** Gemini may propose at most one action. Code expands a **closed, incompatible** set (`close` ⊥ `pause` ⊥ `refund` ⊥ `credit_note`). Independent probes (Jev Choice/Noul **or** same-schema LLM—Jev optional) score each against the **same small state**. Python: if exactly one action has mass ≥ θ **and** no incompatible sibling ≥ θ, execute; if **two or more** ≥ θ, **do not argmax**—emit one discriminating question or halt. Independence of probes is a **feature**: you are testing well-posedness, not a joint world model (Jev does not return joints).

**3-minute demo.** Ticket: “We’re done with the product, maybe park it, maybe shut it.” Left: Gemini `close_account` at high verbal certainty. Right: `close=0.86`, `pause=0.81`—**SPLIT**. No close. **Audience:** add one sentence, “Do not close; freeze billing only.” Re-probe: `pause` unique → commit pause. Show the ledger: close never happened. If both stay high, leave it split; do not fake collapse.

**Why not a wrapper.** Chat still picks a verb. A regex on “pause” misses “park it.” The mechanism is **incompatibility in the action catalog**, which a transcript cannot enforce.

**8.5h MVP and cuts.** Four-action catalog with a declared incompatibility graph. One probe bundle. Simulated billing row. Fixture + one live/replay probe. **Cut:** Jev if `/api/alpha/decisions` misbehaves (keep schema). **Cut:** Modal. **Compressed:** two actions only (`close`/`pause`), hardcoded incompatibility, one fixture pair.

**Kill test (60 min).** Craft state where **each** probe is high in isolation and **both** high together. If you cannot exhibit two highs without dropping both below θ, you have rebuilt a confidence gate—abandon or relabel honestly.

**Deterministic baseline.** Always execute Gemini’s named tool; and always execute `argmax` of the probe vector. SplitBallot must differ on the split fixture and **match** the unique-action fixture (or it is “never act”).

**Falsification.** If every split is just two ~0.5s, it is Breaker. If the incompatibility graph is a single pair you planted, a judge can call it a lookup.

**Risks.** Looks like a safety gate. Using `1-confidence` or multiplying marginals into a fake joint. Audience text as injection (Jev has no defence—constrain to one sentence, don’t let it rewrite criteria).

**Diff from corpus.** Breaker: same refund, stake changes the decision. SplitBallot: **stake fixed, verb set is ill-posed**. Not Unwind/Deal Desk/Airlock.

### 1. Call Time — a stage manager that owns the cue stack

**User and pain.** A director (or tonight: a presenter with two minutes and a hostile clock) cannot both invent a scene and run it. ### 2. Pitch Invasion — a folk game that rewrites itself at half-time
